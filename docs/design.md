# Design and engineering decisions

## Separate planning from authority

The live provider is an ordinary chat-completions client with function tools.
The model chooses actions; the tool registry defines the available capabilities.
Every argument object is parsed as strict JSON and checked against its declared
schema before the tool runs. Unknown tools and extra arguments are rejected.

The structured task is authoritative. The natural-language question provides
context but cannot override its numeric limits or workload fields. A genuine
natural-language constraint parser would need its own validation and evaluation;
this example requires the caller to supply those constraints explicitly.

`compare_runs` accepts exactly the complete set discovered for that workload.
It rejects omitted candidates and mixed workloads. The final tool can reference
only a comparison created during the same session, and must select that
comparison's deterministic winner. If no candidate qualifies, the correct
decision is null. The report is generated by the host from verified values.

This design prevents an unchecked recommendation from being accepted merely
because a model expresses it fluently. It does not establish that the underlying
benchmark metadata is honest or that the measurements are statistically reliable.

## Tool protocol

The engine sends schemas in `tools` with `tool_choice: auto`. It preserves the
assistant's tool-call IDs, returns one tool-role result per executed call, and
continues with those observations. Multiple read calls in a response are
executed sequentially. Decision submission must be a single call.

Tool validation errors are observable and recoverable until the tool-error
budget is reached. Truncated responses, malformed call envelopes, repeated call
IDs, missing tool calls, and exhausted budgets stop the workflow without writing
a successful decision. Failed runs preserve their event trace.

For models whose templates require previous reasoning fields, the HTTP client
preserves returned reasoning metadata in the in-memory conversation. The trace
does not serialize those fields or arbitrary assistant prose. Execution events
are useful for debugging; they are not a claim to expose a model's internal reasoning.

## What is bounded

- A maximum number of model responses and executed tools.
- A deadline checked between operations and passed into HTTP calls.
- A bounded serialized conversation and bounded HTTP response body.
- A small explicit evidence collection with capped file size.
- A limited number of schema/tool errors and transient HTTP retries.

The deadline is cooperative. It is not an OS-level process kill, and a platform's
socket timeout need not preempt every phase of DNS or networking. Model token
budgets, rate limits, tenant isolation, and process resource enforcement belong
in a production execution environment. The byte limit is not an exact tokenizer
context-length calculation; configure the server context for the workload.

## Untrusted evidence

Notes and benchmark strings are data, even when they contain imperative text.
The system instruction makes that distinction explicit. More importantly, the
available tools cannot access arbitrary files, execute commands, or contact an
endpoint selected from a note. Evidence is read only from the caller-selected
workspace, paths must remain within its root, and symlinked evidence is rejected.

The notes test proves that inserted instructions cannot change the deterministic
ranking policy. It does not demonstrate that a live model always ignores prompt
injection. Tool restrictions and final verification constrain the consequence of
bad model choices; prompt wording alone is not a security boundary. Filesystem
checks are not a hardened sandbox against a local attacker racing file changes.

## Evidence and reproducibility

Each normalized record gets a SHA-256 digest of its canonical JSON representation.
This identifies the record's semantic content, independent of JSON whitespace.
An imported vLLM report additionally records the original file's byte digest.
A comparison ID hashes the task, candidate set, metrics, selection, and sources.
These hashes identify evidence; they do not authenticate its author.

The offline provider uses the same dispatch and verification path as the live
provider, but chooses actions with a small deterministic script. Fixture
evaluation demonstrates selection, rejection, and no-evidence behavior. It is
not evidence of an LLM's task-success rate. The HTTP test uses a local scripted
server to exercise the real client protocol without model weights.

## Useful extensions

Add repeated measurements and uncertainty estimates before comparing close runs.
Extend the contract for quality scores, cost, energy, or multiple SLA tiers and
implement a corresponding explicit selection policy. A retrieval index could
replace substring note search while keeping evidence IDs and file boundaries.
Live-model evaluation should include malformed calls, recovery, long contexts,
unsupported claims, and adversarial evidence, with provider/model revisions and
sampling settings recorded alongside results.
